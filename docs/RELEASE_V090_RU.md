# Контроль ИД v0.9.0 — единый Rust + Axum, Bitrix24, роли, RES UI

## Состав
В архиве **только один Rust-проект**. Elixir Phoenix и RabbitMQ больше не используются; на VPS ничего устанавливать не нужно. Браузер открывает домен KeenDNS, Keenetic пересылает HTTPS на Nginx `cloud:443`, Nginx — на `127.0.0.1:8090`.

Новая миграция `010_portal_single_app.sql`:
- шесть фиксированных проектов (не удаляет старые);
- таблица назначения администраторов `bitrix_project_managers`;
- краткоживущие сессии `portal_sessions` с хешами токенов.

Существующие таблицы `documents`, `packages`, `findings`, `ocr_jobs`, `classification_jobs`, `synology_file_index` не очищаются. Существующая миграция `009_bitrix_rbac.sql` сохраняется: `bitrix_principals`, `bitrix_package_acl`.

## Авторизация через Bitrix24
В настройках локального приложения Bitrix24 укажи URL главной/обработчика приложения:
`https://idai.kenreskenres7772023777.netcraze.link/bitrix`

В `.env` в `~/rust/idcontrol` добавь:
```dotenv
BITRIX_DOMAIN=company.bitrix24.ru
LISTEN=127.0.0.1:8090
```
**В v0.9.2 заполнять `BITRIX_MEMBER_ID` не нужно.** Он используется только как необязательный ключ совместимости, если ранее уже назначены права сотрудников в PostgreSQL под этим ключом. В новой установке пространство прав формируется автоматически из закреплённого на сервере `BITRIX_DOMAIN`. Указывай реально принадлежащий тебе домен Bitrix24, без `https://`. Backend **не доверяет** переданным клиентом ID сотрудника: использует access_token только для серверного вызова `user.current` к настроенному домену.

Сессия ставится в cookie `__Host-idcontrol_session` (Secure, HttpOnly, SameSite=None), срок 6 часов, хеш токена хранится в PostgreSQL. Для работы во встроенном iframe браузер должен разрешать cookie третьей стороны для этого приложения. При полном запрете third-party cookies браузером потребуется режим входа через first-party redirect/Storage Access API; эта версия его не реализует.

**Примечание:** `BX24.installFinish()` вызывается только в обработчике установки. Обычная авторизация выполняется через `BX24.init()` + `BX24.getAuth()`, `BX24.callMethod('user.current')` и серверный POST `/auth/bitrix`.

Установи права приложения Bitrix24 на чтение пользователей (для `user.get`), иначе выпадающий список сотрудников не заполнится — числовой ID всё равно можно указать вручную.

## Роли
- **Супер-администратор:** Bitrix24 user ID `1` или `336`, только после серверной проверки OAuth; видит административную вкладку, все проекты и данные.
- **Администратор проекта:** назначается супер-администратором на выбранный ЖК. Может создать комплект выбранного вида работ, создать все 14 разом (повторное нажатие безопасно), выдавать и снимать доступ пользователей к работам.
- **Пользователь:** видит только те объекты/комплекты, на которые получил `bitrix_package_acl`. Роль `uploader` может просматривать и загружать файлы, `engineer` дополнительно проводить проверки/редактировать замечания, `viewer` — только смотреть.

Проверка на сервере действует для пакетов, файлов, результатов, OCR, скачивания и отчётов. Технические `/diagnostics`, `/norms` ограничены супер-администратором. Страница проектов выводит только разрешённые.

## Создание проектов и видов работ
Шесть фиксированных ЖК: Федерация (Куйбышева), OKLAND (Краснодарская), TETRIS (Депутатская/3-я Керченская), КОСМО (Звёздная), PRIME TOWER (Бабефа), DUO (Ползунова). Ручного ввода названия ЖК больше нет. В каталоге 14 видов работ; кнопка **«Создать все 14 видов работ»** не удаляет существующие комплекты или документы.

### Предыдущие данные
Если ранее в `projects` были проекты под другими названиями (например, `тест (esinitsin)` из старой настройки DSM), данные **остаются в PostgreSQL**, но не показываются в новом фиксированном списке. **Не переименовывай и не объединяй проекты SQL-командами, пока не проверишь, какие документы к ним относятся.** Для будущих сканирований нужно указать точное имя ЖК, например `SYNOLOGY_PROJECT_NAME=TETRIS`. Старые документы следует перенести в нужные комплекты отдельной сверенной операцией, не меняя `archive_path` вслепую.

## Обновление Ubuntu
1. Сделай бэкап PostgreSQL (см. `pg_dump -Fc`) и каталогов `storage`/`.env`.
2. Не удаляй текущую папку проекта; распакуй **исходники** из архива поверх существующих с сохранением `.env`, `storage`, `models` и всех пользовательских данных.
3. В существующем `.env` требуется только `BITRIX_DOMAIN`. Если в v0.9.1 уже назначали права, оставь прежний `BITRIX_MEMBER_ID`, чтобы назначения не сменили пространство имён. Новым установкам он не нужен.
4. Выполни:
   ```bash
   cd ~/rust/idcontrol
   cargo check
   cargo run -- --migrate-only
   cargo run
   ```
5. Через Bitrix24 открой `/bitrix` и проверь `GET /api/me` в браузере после входа, затем раздай роли.
6. На `cloud` Nginx уже настроен на HTTPS:443 и Rust:8090, **не меняй маршрутизацию Keenetic**.

Старую миграцию `009_bitrix_rbac.sql` НЕ удалять из `migrations/`, иначе SQLx не сможет подтвердить историю миграций.

## Отладка
```bash
cd ~/rust/idcontrol
cargo run -- --debug-login
```
Включается HTTP Basic **только этим флагом**, имя: `admin`, пароль: `super123`. Отладка действует как супер-администратор на тестовом пространстве `member_id=debug`, и **не должна использоваться на публичном сервере**. Для выхода из режима останови приложение и запусти `cargo run` без флага. Существующая проверка `APP_PASSWORD` в обычном режиме оставлена по прежней договорённости.

## Примечания и ограничения
- Исходная логика OCR, классификации, проверки ИД и Synology не переписана; добавлены авторизация и UI.
- Массовое создание 14 комплектов не означает, что по каждому из них уже загружены документы.
- Снимки предоставлены в качестве визуальных материалов для карточек. Фотографии преобразованы в WebP и хранятся в `assets/projects/`.
- `models/`, `.env`, `storage/` **не входят в ZIP**.
- Проверка компиляции Rust, PostgreSQL и реального портала Bitrix24 должна выполняться на твоём сервере: в среде сборки этого архива `cargo` недоступен. Исходники не следует считать production-tested до `cargo check` и пользовательского тестирования.
