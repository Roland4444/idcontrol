# Контроль ИД v0.6.6 — OCR, задания, диагностика

## Зачем обновление

Ранее `cargo run -- --reprocess-errors` печатал только `Documents to reprocess: 4` и молча ждал выполнения PDF-рендеринга и сетевых вызовов Bitrix VibeCode. Ошибки могли оставаться сохранёнными в PostgreSQL после изменения `.env`.

С версии **v0.6.6** добавлены:

- Сообщения в консоли при рендеринге **каждой страницы PDF** и перед отправкой её в VibeCode.
- Сообщение **каждые 15 секунд ожидания** ответа VibeCode. `VIBE_OCR_TIMEOUT_SECONDS` — таймаут одной HTTP-попытки; для временных ответов 429/5xx предусмотрены повторы.
- Очередь OCR в PostgreSQL (`ocr_jobs`) и журнал событий (`ocr_job_events`). При перезапуске незавершённые задания возвращаются в очередь.
- «**Повторить OCR**» у каждого документа, «**Распознать все с ошибками**» и «**Перераспознать весь комплект**». Последняя операция может создать много платных API-вызовов.
- «**Отменить ожидание**» для задания, которое **ещё не выполняется**; активное обращение к API этой кнопкой не останавливается.
- Раздел **Диагностика / OCR**, автообновление данных раз в 4 секунды, этапы и сообщения, JSON API для мониторинга.
- При ошибке повторного распознавания ранее извлечённый текст больше не затирается пустым результатом.
- Пересчёт правил проводится один раз в конце текущей очереди комплекта, а не после каждого файла.

## Установка поверх v0.6.5 на Windows

1. Остановить работающее приложение в терминале VS Code: `Ctrl+C`.
2. На всякий случай сохранить **старый `.env`** и каталог локального архива (`DATA_ROOT`), если он находится внутри папки проекта.
3. Распаковать полный ZIP v0.6.6; перенести **свой прежний `.env`** в корень `id-control-axum`, рядом с `Cargo.toml`. `.env` с ключами в архив **не включён**.
4. Использовать прежнюю PostgreSQL. База не очищается. При запуске автоматически применяется **новая миграция `006_ocr_jobs.sql`**; ранее применённые миграции не выполняются повторно.
5. Выполнить из корня проекта:

```powershell
cargo check
cargo test
cargo run
```

6. Открыть `http://127.0.0.1:8090` (либо локальный IP сервера, если `LISTEN=0.0.0.0:8090`). На странице комплекта нажать «Распознать все с ошибками». Журнал виден под кнопками. Для диагностики: `http://127.0.0.1:8090/diagnostics`.

Для Windows с PowerShell можно включить подробнее журналы:

```powershell
$env:RUST_LOG = 'id_control_axum=debug,info'
cargo run
```

## CLI диагностика

Команды следует запускать из каталога с `.env` и `Cargo.toml`:

```powershell
cargo run -- --ocr-status
cargo run -- --check-vibe-ocr tests\fixtures\sample.tif
cargo run -- --check-vibe-ocr tests\fixtures\test_2_pages.pdf
cargo run -- --check-synology
cargo run -- --reprocess-errors
```

Последняя команда работает **синхронно** и показывает этапы в терминале. Для новой фоновой очереди используйте кнопки в веб-интерфейсе при работающем сервере. Не запускайте одновременно CLI `--reprocess-errors` и массовое OCR через интерфейс для тех же файлов.

## Веб-интерфейс и мониторинг

- `/diagnostics` — настройки без паролей, состояние Synology, распределение статусов документов, последние ошибки, очередь и журнал событий.
- `/api/ocr/status` — JSON общего состояния; требуется Basic Authentication.
- `/api/ocr/jobs` — JSON последних 100 заданий, `?package_id=N` для фильтрации; требуется Basic Authentication.
- `/ocr/jobs/fragment?package_id=N` — HTML-фрагмент, обновляемый интерфейсом раз в 4 секунды.
- В таблице документов отображаются статус извлечения и рядом — состояние последней OCR-задачи. После завершения для обновления самого текста/классификации страницы нужно перезагрузить страницу.

Статусы очереди: `pending` — ожидает, `running` — выполняется, `done` — распознано, `partial` — частично или нужна ручная проверка, `failed` — ошибка, `cancelled` — отменено до запуска. `extracted` у DOCX/XLSX — это **локальное извлечение текста**, не проверка качества по ГОСТ/СП.

## Форматы и ограничения

- JPG/PNG/TIFF/BMP/GIF/WebP отправляются в VibeCode по схеме успешно проверенного пользователем примера; для TIFF/BMP/GIF сохраняется MIME-совместимость теста (`data:image/jpeg` с исходными байтами). Это поведение специфично для данного API.
- PDF **не отправляется в VibeCode как PDF**. Hayro рендерит страницы в Rust, затем отправляются JPEG-изображения страниц. `pdftoppm` и `tesseract` не требуются.
- В большом PDF обрабатываются не более `OCR_MAX_PAGES` страниц; неполная обработка помечается `partial`.
- Сетевой запрос к VibeCode может длиться до `VIBE_OCR_TIMEOUT_SECONDS` секунд **на одну попытку**; временные ошибки могут повлечь повторы. Ежесекундного progress bar API не предоставляет; для ожидания используется heartbeat через 15 секунд.
- `VIBE_OCR_ENABLED=true` и `VIBE_OCR_KEY=...` должны находиться в **активном** `.env` перед запуском. Перезапуск необходим.
- Проект рассчитан на **один экземпляр OCR-обработчика** для локальной установки; не разворачивайте одновременно несколько одинаковых серверных процессов для одной базы без отдельного тестирования блокировок и пересчётов.
- Basic Auth по HTTP в сети не защищает пароль шифрованием: для эксплуатации нужен HTTPS reverse proxy.

## Сохранённые требования

- Все ранее зарегистрированные документы и версии в PostgreSQL сохраняются; ни один файл на NAS не редактируется.
- Логи и JSON-диагностика **не содержат API-ключей, полных изображений и распознанного текста**.
- `APP_PASSWORD` **не получает порог 16 символов**. В `src/config.rs` оставлена проверка пользователя:

```rust
if password.len()<3 || password.starts_with("REPLACE") || password.starts_with("CHANGE") {
```

## Проверка после распаковки

```powershell
cargo check
cargo test
cargo run -- --ocr-status
```

Если `cargo check` выдаёт ошибки, пришлите **первую** ошибку компиляции и версию Rust `rustc --version` — последующие ошибки часто являются следствиями первой.
