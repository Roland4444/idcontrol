# Контроль ИД v0.6.7.5 — параллельный локальный OCR

## Назначение
Для PDF распознавание страниц теперь выполняется параллельно в пуле обычных потоков Rust (`std::thread::scope`). Каждому потоку выделяется своя ONNX-сессия (детектор + распознаватель); она загружается один раз на время документа. PDF рендерится библиотекой Hayro по страницам. Очередь между рендерингом и OCR ограничена двумя подготовленными страницами на каждый поток; это защищает от хранения сотен JPEG одновременно.

Выходные страницы собираются строго в исходном порядке, даже если страница 8 обработана раньше страницы 7. Ошибка любой страницы не скрывается: OCR документа получает ошибочный статус, прежний сохранённый текст при неудачной переобработке не стирается.

## Конфигурация `.env`

```dotenv
OCR_MODE=local
OCR_PAGE_WORKERS=6
OCR_MAX_PAGES=500
LOCAL_OCR_MODEL_DIR=./models/ocr
VIBE_OCR_ENABLED=false
```

`OCR_PAGE_WORKERS`: от 1 до 16 одновременно работающих ONNX-процессоров на страницах. Для 1-страничного файла — один работник. Общий семафор на процесс ограничивает суммарное число рабочих потоков при одновременной работе сканера и веб-очереди. При нехватке RAM уменьшите значение до 2 или 3.

`OCR_MAX_PAGES`: от 1 до 5000; задаёт максимальное число страниц PDF, которые распознаются. В прежнем v0.6.7.4 значение выше 200 молча обрезалось, теперь это исправлено. Если страниц больше лимита, результат помечается `partial`.

Количество потоков ONNX Runtime *внутри* одной сессии эта настройка не ограничивает. Поэтому на CPU с шестью ядрами обязательно сравните 1, 3 и 6 и измерьте не только время OCR, но и загрузку CPU/RAM. Шестикратное ускорение не гарантируется, а 6 сессий потребляют больше памяти.

## Обновление с v0.6.7.4

1. Остановите сервер `Ctrl+C`.
2. Распакуйте **полный проект** v0.6.7.5. Перенесите свои `.env` и `models/ocr` (либо установите модели по прежней инструкции). Убедитесь, что `DATA_ROOT` и `DATABASE_URL` не менялись.
3. В `.env` укажите `OCR_PAGE_WORKERS=6` и `OCR_MAX_PAGES=500`.
4. Выполните:

```powershell
cargo check
cargo test
cargo run -- --check-local-models
cargo run -- --check-local-ocr "tests\fixtures\test_2_pages.pdf"
cargo run
```

5. Откройте `/diagnostics`. Очередь OCR покажет события `local_wait`, `local_workers`, `render`, `render_queued`, `local_page_start`, `local_page`, `local_done` и ошибки. JSON диагностики `/api/ocr/status` содержит `ocr_page_workers` и `ocr_max_pages`.

Текущие записи PostgreSQL, очередь OCR и версии исходных файлов на Synology остаются на месте. Новых SQL-миграций нет. Сканер продолжает автоматически переподключаться к DSM при ошибках SID 106/107/119 (унаследовано из v0.6.7.4).

## Как измерить ускорение

Попробуйте одну и ту же PDF-копию при значениях `OCR_PAGE_WORKERS=1`, `3`, `6`. После изменения `.env` перезапускайте приложение, выполняйте `cargo run -- --check-local-ocr "путь\к\файлу.pdf"` и сравнивайте сообщения `OCR завершён за ...` и «страниц/мин».

Реальная скорость зависит от размера PDF, скорости рендеринга и характера документов. Чтобы результаты сравнения были честными, проверяйте по одному и тому же PDF на одном компьютере без параллельных тяжёлых задач.

## Ограничения и статус проверки

- OCR не проверяет ГОСТ/СП автоматически и не заменяет инженерную экспертизу.
- Многостраничные TIFF по-прежнему не обрабатываются полностью; они помечаются `partial`.
- ZIP не содержит веса ONNX и ваши секреты.
- На машине сборки отсутствует `cargo` и `rustc`; фактическая компиляция и скорость ONNX должны быть проверены в Windows командой `cargo check`, затем тестовым PDF.
